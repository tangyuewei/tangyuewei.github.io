Agent 走出黑框：Slack Code

唐悦玮 发表于 08-272026-08-27T09:45:00+08:00
16 分钟 阅读

摘要：Slack 在 8 月 20 日推出 Slack Code：把编码 Agent 请进团队频道，计划、差异、预览同屏可见，非工程师也能发起修复，高风险动作需人工审批。这是 AI 编程从单人终端走向多人协作的拐点。

今天大多数 AI 辅助编码，仍发生在视线之外。一个开发者打开私人标签页，把任务喂给 Agent，消失一阵，团队往往要等到一个 PR 落下来，才知道这段时间发生了什么。设想一次线上排查：你让 Agent 修一个接口超时，它在私人会话里跑完、给出 diff、你合并，旁边的前端同事并不知道这次改动动了哪个接口，直到联调时撞上。这种”先合后知”不是某个人不靠谱，而是单人 Agent 工作流的天然形态：上下文散在一个人的会话里，团队没有入口。问题不在于 Agent 不够强，而在于它的工作过程对团队是封闭的——你 merge 了，别人才看见结果；你没 merge，别人连发生了什么都不知道。上篇文章聊”终端为什么顺手”，赞的是它效率；这一篇想补上这份效率的另一面——当 Agent 走出一个人的黑框，进到一屋子人都能看见的地方，事情会怎么变。

8 月 20 日，Slack（Salesforce 旗下）上线了 Slack Code。它做的事很直接：把编码 Agent 从私人终端，搬进团队本来就在用的频道。

Slack Code 做了什么

用法不复杂。你在项目频道里 @一个编码 Agent——首发支持的是 Anthropic 的 Claude Code、Cognition 的 Devin、GitHub Copilot 和 Vercel——它就会围绕这个任务，自动开一个专属的”代码频道”，把需要参与的人拉进来。

频道内部用几个标签页把工作拆开：对话、计划、代码 diff、以及实时的 HTML 预览。不再是从一长串聊天记录里翻答案，而是计划、改动、效果各归各位，谁都能在同一个地方看到进展。在官方演示里，一个设计师在 Devin 的任务里丢了张 Figma，Agent 把它揉进了实现；非工程师也能用日常语言描述一个问题，让 Agent 准备好改动，再拉工程师进来 review。

Slack 自己在官方博客里披露了一个数字：超过 70% 的代码频道，从想法到合并 PR，在一天之内开合。这个数字要会用——它是 Slack 自家、正式发布前统计的数据，没有公布分母。看它的”形状”就够了：这个产品押注的工作单元是”当天能收口的小任务”，不是你那个拖两周的迁移工程。ChatGPT 被列为”即将接入”，说明 Slack 想做的是容器，不是某个模型的自留地。

四个伙伴接进来，用法并不一样。Claude 在被 @时开频道、做完自动归档；Devin 更像”一个同事”，需要时响应、不需要时安静；GitHub 的集成让非技术同事用自然语言描述问题、Agent 准备改动、再拉工程师 review；Vercel 则在改动后生成可分享的实时预览链接。Slack 把桌子摆好，具体怎么吃这顿饭，各家 Agent 自己定。

它对所有 Slack 套餐开放，包括免费工作区——这意味着它不是企业版独享，而是面向全体用户基数的一次发布；当然，各家 Agent 自己的订阅仍要单独买。容器免费，干活的不免费。

为什么是频道，而不是又一个标签页

Slack 做这个形态，是吃过内部苦头的。复杂、多轮的 Agent 执行塞进普通消息列，又局促又吵；塞进私人标签页，又丢掉了 Slack 最值钱的东西——透明协作。代码频道想给 Agent “一张能入座的桌子”：既够宽敞，又不离开团队已经在聊的地方。这不是 Slack 拍脑袋。早在 2025 年底，Anthropic 就演示过从 Slack 线程里委派 Claude Code；之后 Slack 自己接连放出 MCP server、Slackbot 的 MCP 客户端。Slack Code 是把这些零散能力收拢成一个正式的产品形态。

落到具体，是三件事：

实时可见。 diff 和预览在合进主干之前就能看到，你评论一句”这个接口形状换个样子”，Agent 下一轮就把方向改了。重定向的成本发生在最便宜的时候，而不是 PR 已经发出、大家才开始挑刺。

人工审批门禁。 合生产这类高风险动作，不会由 Agent 自己拍板，而是路由给一个具体的人，在频道里签。原文的说法是”就在频道里，快速批准”。没有任何改动是 Agent 自己说了算落地的。

审计留痕。 任务做完，频道自动归档，但内容留在 Slack 里可搜索。谁改的、谁批的、走了哪条路径，三个月后还能 grep 出来。它把”草稿分支的临时感”和”合规系统的纸面痕迹”合在了一起——这是个挺巧的设计， Slack Code 把这两样一次性打包拿来了。

Slack 自己把这类工作的范围说得很克制：bug 修复、进 backlog 的小界面改动，而不是架构级的大动作。它赌的是”小步快跑、当天收口”，不是替你重写系统。

还有个容易被略过的细节：Agent 继承你已有的 Slack 权限和安全策略，它看得到的，就是你本来就允许它看的。这是对的默认，但也正是一句安全团队会想自己验证、而不是照单全收的话。

把 Agent 关在私人标签页里，省了别人的打扰，也省掉了别人的校正。等到 PR 落地，能挑刺的人已经晚了一步。频道反过来，把校正提前到了 Agent 还在干活的时候。代价是噪音——这件事下面会专门聊。

国内同行走到哪了

把视线拉回国内。协作平台一侧，某书智能伙伴、某钉 AI 助理、某企微 AI，都已经把 AI 助理请进群聊和文档协作。编码 Agent 一侧，字节的 Trae 把写码、改界面、出设计图收进同一个 AI IDE；Qoder 在 IDE 之外还给了命令行，习惯终端的人也能用；CodeBuddy 同样走 IDE 加 CLI（8 月初写过一篇）。它们的共同点，是把 Agent 接进你已经有的工作界面，而不是另起炉灶。方向是一致的：把 Agent 嵌进协作发生的地方，而不是让它孤零零地待在某个人的编辑器里。

但要诚实地说一句：国内”编码 Agent 进团队频道做 review 门禁、自动归档审计”这个具体形态，还早。这几家目前更像是把 Agent 放在 IDE 或 CLI 里单人使用，或者把 AI 助理接进群聊做问答，还没有把”计划 / diff / 预览同屏 + 人工审批 + 可搜审计”打包成一个频道类型。产品化路径不同，别把国外已经发生的，当成国内已有的。实际以各家官方文档为准。

值得记一笔的是 Slack 把”协作”当成了 AI 编程的下一层，而不是只盯着”模型更强”。当代码生成快到不再是瓶颈，瓶颈就挪到了谁来决定写什么、谁来把关——那恰恰发生在人和人之间，而不是人和模型之间。这一点，国内外团队迟早都要面对。

往后看半年到一年，”编码 Agent 进协作空间”大概率会从 Slack 一家，变成一类默认期待。国内协作平台和编码 Agent 迟早会在”频道化 review”上相遇——只是节奏和形态，还要看各家把权限、审计、审批这三件事做到多扎实。

别只算收益账

频道让过程可见，但可见不等于写得好。房间里人多了，评论一个接一个，Agent 照单全收，方向反而可能被带偏。谁的反馈算数、review 到什么粒度，公司得自己定，不是开了频道就自动解决。Slack 把审查量交还给团队，本身就是一笔要算清楚的账。

一个比喻很贴切：私人标签页像在封闭办公室里吩咐助理，频道像在开放式工位里吩咐同一个助理。助理能力没变，但开放式工位里谁都能插话，它也分不清哪句话来自真正拍板的人，尤其在人多的频道里。Slack Code 把房间打开了，价值在这，要你接住的责任也在这。

所以更务实的判断是：小团队、review 距离短、彼此信任基础好的，最容易吃上这波红利；跨时区、角色多、彼此不熟的大房间，先把”谁能在频道里下指令”这条线画清楚，再谈效率。

权限也是一样。Agent 继承了频道的身份，但仓库、凭证、它能触达的外围系统，范围仍要单独评估。频道只是把”屋里多了个能办事的”这件事，从黑盒里拎出来、摆到了台面上，并没有替你回答”它到底该有多少权限”。更现实的是，频道里每个人都能给 Agent 下指令，一旦有人贴来一段来路不明的代码或一句带诱导的话，Agent 可能照做。Slack 的权限继承挡不住”指令本身有毒”——它自己在文档里也提醒，只在你信任的对话里用 Agent。

Slack 临时 CEO Rob Seaman 在发布时表达过一个判断：代码不再是瓶颈，瓶颈变成想法、品味、判断、手艺；而 Slack Code 是把更多人接进”贡献想法”那一端，而不是替你把判断做了。这话说得克制，也点透了——工具拉长的是人的能力半径，不是替人免除判断。

所以对团队，Slack Code 不是装上就更好的工具。它把协作的透明度做成默认，却也把”谁来把关、怎么把关”的难题推到台前。会用的团队，拿它缩短 review 距离；不会用的，只是多了一个更吵的地方。

回到开头。
