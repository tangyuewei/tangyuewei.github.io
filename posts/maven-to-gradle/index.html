换构建系统，AI 全绿也白干

唐悦玮 发表于 09-092026-09-09T09:10:00+08:00
10 分钟 阅读

摘要：给 AI 一个真实项目，让它把 Maven 换成 Gradle、行为分毫不差——新基准 SWE Refactor Bench 专测这类整仓重构。520 次运行通过率仅 5.4%。测试全绿，从来不是迁移成功的证据。

你丢给 AI 一句话：”把项目从 Maven 迁到 Gradle，外部行为不能变。”

它埋头跑了几小时，回来汇报：测试全绿。

听起来像成了。但 2026 年 8 月底，Navers Lab（Einsia AI）联合清华大学放出一个新基准 SWE Refactor Bench1，专门验这种事。

20 道”整仓换技术栈”的题，8 个前沿模型、26 种配置一共跑了 520 次，只有 28 次通过全部关卡——通过率 5.4%。20 道题里，13 道没有任何模型做出可接受的答案。

测试全绿，在迁移这类任务上，从来不是成功的证据。

修复从红开始，迁移从绿开始

为什么全绿不能信？基准论文2给这种失败模式起了个名字：盲区（Blindness）。

修 bug 的任务天然是”从红到绿”：测试先失败，你改完它通过，这一跳本身就是活干完了的证据。

迁移是另一种任务。它从绿开始——原仓库本来就能通过自己全部测试。你把仓库一行不改原样交回去，测试照样全绿。

于是测试在这里回答的问题是”有没有弄坏什么”，而不是”有没有真的换掉”。评测如果只跑测试，等于在奖励什么都不干。

作者在论文里把这句话写得很直白：过行为测试的提交，可能是真迁移，也可能是空 diff——套件区分不了。

三道关卡，一关不过即出局

SWE Refactor Bench 的应对，是把一次迁移拆成三道串联的关卡。

第一关：迁移审计（Migration Audit）。 检查旧技术栈有没有从”实际构建出来的产物”里彻底消失。

注意，它读的是机制，不是字符串——pom.xml 删没删不算数，Gradle 打出来的 jar 里还残留 Maven 的痕迹才算数。这一关有一票否决权。

第二关：行为测试。 130,118 项从原始系统录下来的检查，一项不过，整次归零。

第三关：Agentic Verification，最狠。 六个独立的 coding agent，各给一小时，专门来挑你这套”已迁移”代码的行为差异——只有能跑出来的可执行反例才算数。

换算到你的团队：第一关是”审查看的是产物不是 diff”，第二关是”海量回归断言”，第三关是”找一个不信任你的同事来挑刺，挑不出来才放行”。

8 个模型，只有榜首接近及格

结果有多惨，看榜单就够。满分 100，榜首是 claude-opus-5 的 xhigh 配置：47.0 分，20 道题完整做出 5 道，平均每题烧 74.9 美元。

第二名 gpt-5.6-sol 只有 28.5 分，做出 4 道，每题成本却飙到 143.5 美元——比榜首贵一倍，分还差一截。国产开源模型 Kimi K3 排第三，19.5 分。

比总分更值得琢磨的是失败分布。

520 次里有 340 次确实动手迁移、过了第一关。但过审的运行里，58% 能把行为恢复到 99% 的检查——就差最后一口气。

可只有 26% 做到 100% 全对。而这 100% 全对的那些提交，又有三分之二栽在第三关：被验证 agent 在一小时内找出反例。

换句话说，差距全在”最后一英里”：把迁移大体做完容易，做到分毫不差极难。这跟真实工程里”看着好了，上线就炸”是同一个结构。

构建工具类，是四类里最简单的

四类技术债的难度差得很远。语言重写（C→Rust、Python→Go 这类）得分只有 5.6；框架迁移（Vue→React、Flask→Starlette）11.98；平台移植（POSIX→WASI）17.18；最容易的是构建工具链迁移（Autotools→CMake、Maven→Gradle），31.41。

原因不复杂：构建迁移的改动集中在配置和元数据——依赖坐标、插件、生命周期，语义相对封闭。

语言重写要把语义、接口、运行时行为整个搬一遍，一处偏差就出局。

注意，20 道题里那道 Maven→Gradle，迁移对象是 Gson 2.10.1——19k 行，多数 Java 项目都用过的 JSON 库。

Gson 这道题归在”最容易”的一类里，可具体到它，所有配置里最好的尝试也只拿到 70 分——迁移做了大半，没一次真正收尾。

人该守的三道闸

生产环境没有 130,118 项现成检查，也没有六个 agent 替你挑刺。这三道闸，得人自己搭。

闸一：看产物，不看 git diff。 别因为 AI 删了 pom.xml 就宣布迁移完成。检查 Gradle 实际构建出的 jar/war：有没有残留 Maven 插件生成的资源、MANIFEST、依赖解析路径；用 ./gradlew dependencies 和 mvn dependency:tree 对一遍版本坐标。

旧技术栈必须在产物里消失，而不只是从源码里消失——这正是基准第一关的工程版。

闸二：把”绿”定义得足够厚。 迁移前先冻结一套基线：全量测试、依赖树、产物清单、打包内容。迁移后逐项比对。scope 映射错一次就够你喝一壶，最典型的就是这一组：

版本更是一个都不能漂。

闸三：别让干活的人自己验收。 要么找一个没参与迁移的同事做代码审查，要么双轨灰度：Maven 和 Gradle 并存一段时间，同一份输入对比两边产物。

基准第三关的本质，就是”换个不信任的脑子再查一遍”——这条纪律在生产里同样成立。

别把”AI 能做”读成”你应该迁”

最后把立场说清楚：这个基准不是劝你把 Maven 换成 Gradle。

Maven 稳定、成熟、团队有肌肉记忆。项目没有痛点就不迁，这是工程常识，跟 AI 会不会没关系。

基准里出现 Maven→Gradle，只是因为它是”整仓重构”的一个标准样本——用来量 AI 的能力边界，不是给你发迁移许可证。

它真正给出的信号是另一件事：能把代码改到测试全绿的 agent，离”独立完成一次系统级重构”还很远。中间的差距，就是人在审什么、验什么、守哪几道闸。

而这几道闸，今天还得人来搭。
