前端和后端，转 AI 全栈怎么转

唐悦玮 发表于 11-272026-11-27T11:53:00+08:00
12 分钟 阅读

摘要：转 AI 全栈，前端缺的是边界，后端缺的是不确定。两条路看着分岔，卡人的地方却是同一张验收单：你能做出东西，还得敢在上线单上签字。这篇分开讲各自怎么补，也说清最容易走错的那两步。

这一周看到两份招聘启事，看完觉得挺有意思。

一份挂的是前端岗，职责里写的却是 Agent 服务编排、多端 SDK、云平台。另一份挂的是后端，要求放在最后一行，有 LLM 应用开发经验优先。

名字不一样，干的活其实是一件事——把 AI 功能从界面一路做到上线。

两份 JD 摆在一起，比什么趋势报告都直白。

先把结论放这儿。前端和后端转 AI 全栈，缺的东西不一样。

前端缺的是边界，后端缺的是不确定。方向要是补反了，两边最后都卡在同一个地方——东西能做出来，就是不敢上线。

我自己是写 Java 的。这一年多，把手上几个服务一个一个接上了界面。

招聘数据里，这两条路早就分开了

先看数据。

2026 年 9 月，人才平台 Andela 发了一份研究，拆了财富 500 强的 47,101 份技术岗招聘启事，一共 2,026 项技能。

标题写着“AI 工程师”“ML 工程师”的，有 1,832 份。这 1,832 份里头，53% 要求你会至少两种岗位的技能。

研究负责人 Cory Hymel 跟 Stack Overflow 说了一句话，我觉得挺硬：

We didn’t see in the data this idea of a net generalist.

翻成中文就是，数据里根本没有“什么都懂一点”的通才岗位。

那企业到底想要什么人？报告里有个说法，叫技能渗漏。

意思是，技能会从一条岗位的边界，慢慢渗到隔壁去。前端往产品定义那边渗，后端往“把模型部署进生产”那边渗。方向正好相反。

出身 手上已经有的 要补的那块
前端 状态、交互、空态 数据边界与失败路径
后端 隔离、幂等、超时 非确定性与成本上限

两边都缺的那件东西，是签字。

前端缺的是边界

先说个你肯定见过的场面。

AI 帮你写完一个表单页，提交按钮有，loading 有，成功提示也有，看着挺完整。

可断网了呢？接口返回 409 呢？用户手快，连点三次呢？

这些状态，AI 不一定会写，但你一定会查。这是你的本钱，别丢。

现在还多了一种情况，就是流式输出。

首字还没到，是一种情况。中途断了，是另一种。正常收尾，又是一种。

AI 写的流式界面，一般只处理开头和结尾。中间一断，它就在那儿一直转圈。

这三种情况怎么区分，断了以后怎么重来，靠的还是你带过来的经验。

真正的问题在另一头：页面拿到的那份数据，能不能给别人看。

我举个真事。

Next.js 16 在 2026 年 11 月发了个安全版本，修掉 CVE-2026-119790。受影响的是 16.3.0 到 16.4.4，16.4.5 修好。

问题出在一个用了 'use cache' 的函数上。渲染的时候，它先被直接调了一次，后来又被 unstable_cache() 包了一层，又调了一次。

冷启动那一下，跨请求去重让后一次调用搭了前一次的车，结果拿到了别的租户的数据。

存缓存的时候，key 里没带区分租户的 root 参数。

1
2
3
4
5

// 示意：readSettings 内部是 'use cache'，外面又包了一层
export const getSettings = unstable_cache(
  async (tenant: string) => readSettings(tenant),
  ['settings'],            // 这层 key 里没有 tenant
);

你看，语法没错，类型也没错，AI 写出来也是这个样子。错的是隔离，key 里少了一个租户。

按公告的说法，这种嵌套本来就该报错。只有冷启动那个窗口能漏过去，所以测试也抓不到。

写页面的直觉是，缓存归框架管。做过多租户的直觉是，缓存 key 里必须带租户。

前端转 AI 全栈，要装的就是后面这个直觉，不是再学一门语言。

前端这边先说到这儿。后端是另一摊事。

后端缺的是不确定

隔离和失败路径，这是后端的老本行。幂等键、超时降级、补偿任务，写过几百遍。

模型这东西，跟支付网关其实一个性质：会超时，会抽风，价格也会变。区别只有一个，它不保证同样的输入给你同样的输出。

1
2
3
4
5

// 模型调用当外部依赖：限时、兜底，别让它拖死线程
var answer = CompletableFuture
    .supplyAsync(() -> llm.chat(prompt), llmPool)
    .orTimeout(20, TimeUnit.SECONDS)
    .exceptionally(e -> fallback.answer(prompt));

这么写，产品会显得有点笨。模型挂了，就回一句“稍后再试”，它不会自己想办法。

可笨一点，总比卡死强。

真正难的不是这段代码，是代码后面那笔账。

同一个请求，用户手一抖重试了两次，你到底扣几次费？

这就是后端最容易漏的地方。模型的不确定，最后不体现在接口返回里，体现在账单上。

解法不新鲜。给每次业务动作发一个幂等键，命中就直接返回上次的结果，token 也顺手省了。

还有一处也容易漏。模型失败，别直接抛 500。

页面分不清是服务挂了，还是参数错了，用户那边只看到一个白屏。

最后签字的，只有你

前面这两块补完，还有一件事没人能替你干：把东西交出去，签上自己的名字。

一个人负责上线，出了事，没人可推。

日志里至少得有三样：request id、这次花了多少 token、端到端用了多少毫秒。

这张单子，不会因为你出身前端还是后端，就变短一点。

有些路，我不建议走。

前端那条，是跑去补 Java 分层、啃 Spring 全家桶。

Andela 把“产品前端工程师”单列成一个新岗位，意思是前端要往产品定义上伸，不是往“再多会一门后端语言”上伸。

后端那条，是跑去啃 PyTorch、预训练、显存估算。报告里给“LLM 应用工程师”的定义很清楚：基于基础模型做应用，不是训练基础模型。

真想训模型，那是 MLOps 流水线工程师的活。

这两条路看着不一样，最后都落到同一件事上：往上走一步，自己拿主意。

装修这事最能说明白。AI 把墙刷了，地也铺了，看着像模像样。可水电是你自己验的，验收单上签字的也是你。

门开在哪儿，插座留几个，跳闸了谁去合闸，这些它替不了。

你现在就可以打开手上那个“AI 帮我写完”的页面，问自己三句话。

数据库里换个租户 id，这页面会不会显示别人的数据？

模型接口挂十分钟，用户看到的是什么？

这个月账单翻了三倍，你从哪张图里能看出来？

三句都答得上来，说明你已经跨过去了。答不上来，就是缺的那块还没补上。

最后捋一遍。前端缺边界，后端缺不确定，补完以后，面对的是同一张单：你签不签得下去。

顺序也别搞反。边界和兜底在前，界面在后。界面 AI 写得比你快，但验收这一步，它替不了你。

下次再看 AI 全栈的 JD，先数一数它要你对哪一段负责，再数它要几门语言。
