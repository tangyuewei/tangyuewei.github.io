> **摘要**：技能文件里那个叫 allowed-tools 的字段，看着像权限系统。官方文档写着：它只免除询问，不限制可用工具，而且技能可以给自己授权。格式能写下名字和描述，写不下的是它能碰哪些路径、连哪些主机、用哪份凭据。

装一个技能的时候，你看到的是两行字：一个名字，一段描述。

你点下"同意"，是冲着这两行字点的。

到了周四，一个看上去毫不相关的仓库任务触发了它，跑起来的是 `scripts/` 目录里的 Python，用的是你终端里的凭据、你的仓库、你的网络出口。它在你按下同意的那天，和它真正干活的那天，中间隔了三天，也隔着你从没看过的那些代码。

这不是某一个技能的问题。根子在格式——**SKILL.md 这个文件格式里，没有地方可以写"它被允许做什么"。**

![格式能写下的字段，和写不下的那些约束](/imgs/202609/2026-09-17-skill-permission-gap-infographic-1.jpg)

## 那个像权限的字段，官方定义是"免询问"

Agent Skill 的规范里有个字段叫 `allowed-tools`。名字起得很像权限系统：allowed，被允许的。

先看规范怎么说。agentskills.io 的规范原文是这么定义的：一个用空格分隔的、**预先批准**的工具列表；紧跟一句"实验性，不同 Agent 实现的支持程度可能有差异"（Experimental. Support for this field may vary between agent implementations）。

再看客户端怎么说。Claude Code 的文档把它解释得更直接：

> Tools Claude can use without asking permission during the turn that invokes this skill. The grant clears when you send your next message.

翻译过来：本轮对话里，列出的工具**不用再问你**。你发下一条消息，这个豁免就过期。

关键在于下一句，它把语义钉死了：

> It does not restrict which tools are available: every tool remains callable.

**它不限制哪些工具可用，所有工具依然可调用。**

这就是全部差别。`allowed-tools` 是"别弹窗了"，不是"只能做这些"。前者是免打扰设置，后者才是权限边界。两者在配置文件里长得几乎一样，在出事时的差别是：一个拦得住，一个拦不住。

更值得留意的是同页文档里的一句提醒：工作区信任（workspace trust）对话框管不到这个字段。也就是说，你从没信任过的目录，只要技能被调用，它声明的 `allowed-tools` 照样生效。原文写得很坦白：

> A skill can grant itself broad tool access.

**技能可以给自己授予宽泛的工具访问权。**

这句话不是我推的，是文档自己写的。一个文件，可以替自己批准自己。

## 规范能写下的，和写不下的

把规范的六个字段摊开看，会发现一件事：**它对名字的约束比对行为的约束细得多。**

`name` 有硬性限制——最多 64 个字符，只能用小写字母、数字和连字符，不能以连字符开头结尾，不能有连续连字符，还必须和目录名一致。规则细到这种程度。

`description` 最多 1024 字符。`license` 是许可名或捆绑许可文件的文件名。`compatibility` 最多 500 字符，说明环境要求。`metadata` 是个随便你填的字符串键值对。最后就是那个实验性的 `allowed-tools`。

六个字段，能表达的全部信息就这些。

那么写不下的是什么？

- 能读哪些路径
- 能连哪些主机
- 能用哪一份凭据
- 能起哪些子进程
- 单次跑多久算超时
- 输出多大算异常

这些都是权限的实际内容。规范里一个都没有。

有人把这件事说得比我说得准。一份安全厂商的技术分析里有个判断值得抄下来：`allowed-tools` 听起来像权限系统，但**它命名的是工具，不是权限**。

`Read` 没有回答哪些路径。`Bash(git add *)` 没有回答哪个仓库、哪个远端、哪些凭据能推上去。

工具名是个名词。授权是一组带范围和条件的动词。一个名词装不下。

## 有执行的地方，没有边界

如果规范里没有任何可执行的东西，这个缺口还只是理论问题——纯 Markdown 文件最多骗骗模型。

但规范同时定义了另一个目录：`scripts/`。原文是"Contains executable code that agents can run"，放的是 Agent 能跑的代码，推荐的常见选项是 Python、Bash、JavaScript。

同一份规范里，还顺手给了作者一个便利：文档里的示例展示了技能调用 `uvx`、`npx`、`bunx`、`deno run`、`go run`，这些包在执行的那一刻才解析。

于是就有了这么个组合：

**一个标准的、放可执行代码的位置，配上一句"支持哪些语言取决于 Agent 实现"，以及对这段代码能读什么、连什么、起什么，零字节的约束。**

更麻烦的是，这段代码跑在什么身份上。AppSec 这套工具链里，没有哪个环节会去读 Markdown——依赖扫描工具查的是依赖树和漏洞公告源，而技能没有公告源；资产管理系统里压根没有"技能"这个类别，装一个技能不会产生 CMDB 记录，也不会产生 IAM 关联。

结果就一句话：技能继承的是宿主 Agent 的全部环境权威。**没有"每个技能一个身份"这种东西可以拿来收窄，所以任何一个技能的爆炸半径，就是整个 Agent 的爆炸半径。**

OWASP 在 `Over-Privileged Skills` 这一条里举了两个例子：一个"天气助手"读走了整个 `.env`，一个本该只做 SELECT 的技能被说动去执行 DELETE。这一条的原话是——"权限检查发生在工具调用处，而不是意图处"（permission is checked at the tool call, not at the intent）。

## 时间差：周一装，周四跑

技能是逐步加载的。这个设计本身没问题，甚至是它能在生态里铺开的原因。

- 启动时，Agent 只看得到每个技能的 `name` 和 `description`，大约 100 tokens
- 任务匹配上描述，才加载完整的 SKILL.md 正文（建议 5000 tokens 以内）
- 正文里指向了某个文件、某段脚本，那一刻才会去读、去跑

这是很好的上下文管理。放在安全上看就是另一回事了——**这是一套延迟执行的时序。**

周一，你审查的是两行字。周三，那个 `.env`、那份 git 凭据、那串云密钥还在你的环境里，只是技能还没动。周四，一个不相关的任务让某段描述匹配上了，正文加载，脚本执行，它读走了周边项目的配置文件，用你已经登录的凭据发出去，然后返回一份看起来正常的报告。

整条链里没有一步需要内存破坏漏洞。**技能要求的每一项能力，你的 Agent 本来就有。**

OWASP 上周定稿的《智能体技能十大风险》把这个机理放在了第 4 条 `Insecure Metadata` 里，原话是：

> The manifest is attacker-controlled input, parsed with the agent's full permissions before any user action.

清单文件是攻击者可控的输入，在你做出任何动作之前，就已经以 Agent 的完整权限被解析了。

这句话值得停一下：不是执行的时候才危险，是**解析元数据的那一刻**就已经在完整权限下了。

风险 1"恶意技能"里挂的官方案例是今年 2 月的 ClawHavoc 事件：**1,184 个恶意技能，来自 12 个发布账号，共用同一个 C2 地址**，投递的是针对 macOS 钱包、SSH 密钥和浏览器凭据的窃取程序。

另一个例子更能说明扫描为什么失效。今年 7 月初，有人仿冒一个智能体平台注册了近似域名，同时放出木马化的 Python 包和武器化的技能。自动扫描器几小时内就检出了 Python 包，**技能却全部漏过**，每个累积了 30 万次以上的安装。

扫描为什么拦不住？OWASP 专门列了一条 `Poor Scanning`：技能天然是自然语言和代码混在一起的东西，市场部署的模式匹配、正则和签名检测天生看不住它。公开记录里，Trail of Bits 把当时能拿到的技能扫描器逐个试了一遍，全部在一小时内绕过；Adversa AI 在自己测试里绕过了 8 个扫描器。最讽刺的一个细节是，某个技能市场自带的"技能卫士"扫描器本身就是个技能，被攻击者拿去当可信度背书用了。

![从装下到触发：三段延迟，和那一刻拿到的身份](/imgs/202609/2026-09-17-skill-permission-gap-infographic-2.jpg)

## 分发已经成熟，授权还是空白

最能说明问题的是当下的时间线：**这个生态在"怎么把技能送到你机器上"这件事上已经相当成熟，在"它能做什么"这件事上还是空白。**

9 月 5 日，mise 的作者 Jeff Dickey 发布了 packslip，一份签名的发布清单：把版本锁定、签名验证、下载字节校验都做了，还把技能激活改成需要显式选择加入（opt-in）。这是很扎实的供应链工程。

但它自己在发布说明里把边界划得很清楚：**一份验证过的签名告诉你指令从哪来，不告诉你这些指令适不适合你的项目。**

同一条时间线上，X 发布了自己的官方技能，通过一个 well-known 端点就能被发现，一条命令装上：

```
npx skills add https://docs.x.com
```

另一头，Hacker News 首页有个 100 多条评论的讨论帖，聊怎么管理技能文件。Git、软链接、版本锁定、包管理器、evals、捆绑脚本，都聊到了——**"permission"这个词一次都没出现。**

这不是谁疏忽了。这是整个生态当前的注意力分配：先把分发做顺，授权的语法还没开始设计。

有一份技术分析把这层落差总结得挺准确：生态在学会怎么分发和维护技能，但还没就"怎么框住技能能做的事"达成一致。清单可以描述请求的权限，**但必须有技能之外的东西去执行它。**

跨平台这条线更直接。OWASP 第 10 条 `Cross-Platform Reuse` 的原话是：技能在 OpenClaw、Claude Code、Cursor、VS Code 之间流转，**它们的安全元数据不会跟着走**。一个 `risk_tier: L3` 的风险标记，被移植到一个没有这个字段的格式里，就消失了；一份权限清单被剥掉后，技能继承的是目标平台更宽松的默认值。

换个说法：你为技能加的任何一层安全标注，都是某个平台的私有约定。它能被剥离，而且会被剥离。

## 边界只能画在技能外面

那 `allowed-tools` 到底还有没有用？有，但它是个**提示**，不是**边界**。当免打扰设置用是合适的——少弹几个窗，让常规操作顺一点。把它当审批闸门用，方向就错了。

真正的边界得画在技能外面。四件事按性价比排：

**第一，凭据不进环境变量。** 技能本质上是不可信输入——把密钥放进它能读到的环境里，等于把家门钥匙交给网友。这条不是我打的比方，OWASP 给技能使用者列的建议里，它排在前几位。

**第二，脚本进沙箱，靠的不是声明。** 隔离是运行时的事，不是文本里的事。技能里写什么都不构成隔离——沙箱要由宿主提供，由操作系统或容器执行。

**第三，出站做白名单。** 前面那条攻击链里最关键的一步是"发出去"。DNS 查询、HTTP 请求、隐写信道，这些都得在网络的出口上管，而不是在技能文件里管。

**第四，把目录信任的颗粒度收细。** 现在的信任模型是把整个文件夹当成你的，别人仓库里的技能也跟着变成你的。这个模型的原文表述是"信任授予给文件夹，文件夹里的一切都算你的"。听起来省事，代价是仓库里任何一份 Markdown 都可能带着执行计划进来。

![四条边界，都画在技能文件之外](/imgs/202609/2026-09-17-skill-permission-gap-infographic-3.jpg)

国内这条线也在动，而且动得比想象中快。

7 月 2 日，国家标准化管理委员会下达了《智能体应用安全基本要求》强制性国家标准计划，计划号 20263116-Q-252。这是全球首部面向智能体安全的强制性国家标准，由中央网信办归口，中国移动、中国电子技术标准化研究院、国家计算机网络应急技术处理协调中心牵头起草。

值得注意的不是"又出了一个标准"，而是它把强制内容写在哪几个词上：**身份标识、系统权限调用、工具调用、高风险操作人工介入、日志留存与动态监测、异常阻断与紧急关停**。

"系统权限调用""工具调用""高风险操作人工介入"——正好是这篇文章在讲的这三件事。配套的动作也在同步：7 月 1 日，全国网安标委发布了《智能体部署使用安全指引》实践指南。

更早一点，今年 3 月有公开报道提到，中国信通院副院长魏亮在人民网的一次采访里点了开源智能体 OpenClaw 的名：信任边界模糊，技能包市场缺乏严格审核。

而在标准之外，OWASP 自己也在补格式的那一半：这次发布 Top 10 的同时，放出了一个 **Universal Skill Format** 的初始草案，试图用一份标准化的 YAML 让自动化分析判断哪些技能可信。从公开介绍看，这份格式的第一节就是来源信息。

方向很清楚：**先给格式补上安全元数据，再让工具链去消费它。**

## 总结

一句话：SKILL.md 里那个像权限系统的字段，不是边界。它说的是"别问了"，不是"只能这样"。

规范能写下名字、描述、许可、环境要求，和一个实验性的工具名单。写不下的是它能碰哪些路径、连哪些主机、用哪份凭据。而同一份规范又给可执行代码安排了标准位置。

在这个语法补上之前，能靠的只有技能外面的东西：凭据别放进它能读到的环境，脚本进制运行时的沙箱，出站走白名单，目录信任别一把梭。

一个文本文件，不应该有能力扩大 Agent 能碰的范围。
