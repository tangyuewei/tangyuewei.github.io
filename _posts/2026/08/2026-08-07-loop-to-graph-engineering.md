> **摘要**：Loop Engineering 才火六周，AI Coding 圈就开始谈 Graph Engineering。这不是炒作接力，而是 Agent 编排的下一层：当多个 Agent 组队协作，问题从"怎样让它继续做"变成"这些工作怎么连接"。本文讲清两者关系，以及什么任务才值得上 Graph。

## 从一个具体问题开始

先讲个时间线。

6 月下旬，Peter Steinberger——OpenClaw 的创造者——说了句"别再亲手提示 Coding Agent，去设计能提示它的循环"，Loop Engineering 就这么火了。

六周后，还是他，在 X 上问："我们还在谈 Loop，还是已经转向 Graph 了？"这条帖子到 7 月 28 日，约 307 万次浏览。

同一天，Hamel Husain 发了一篇调侃文章，《Loop Engineering Is Dead. Enter Graph Engineering》。正文只有一张写着 "Stop it" 的动图，却拿了约 68 万次浏览。

一个半开玩笑的提问，一个周末就变成了 AI Coding 圈的热词。

很多人还没把 Loop 用明白，Graph 就来了。这事值得停下来想一想：到底是炒作接力，还是真发生了什么。

## Loop 解决不了的新问题

先说 Loop 是什么。

一个 Coding Agent 写完代码，跑测试，报错了，自己看日志、改代码、再跑，直到通过。这个"写-测-改-再测"的自我闭环，就是 Loop。

Loop 解决的是"单个 Agent 怎么持续把事情做对"。

但项目一大，问题就变了。研究、实现、测试、审查，这些活一个人干不完，得几个 Agent 分工。这时候你面对的，不再是"怎样让它继续做"，而是这些工作之间怎么连接。

谁先做，谁后做，结果传给谁，失败回退到哪，谁能改共享状态。Loop 不管这些，管这些的是 Graph。

Graph 就是任务编排系统：管理多个工作单元之间的连接、共享状态和路径选择。

## Graph 是什么：四个要素

Graph 不玄乎，就四样东西：节点、边、共享状态、路由规则。

**节点（Node）**：承担某种职责的工作单元。可以是一段确定性代码、一次模型调用、一个工具，也可以是一个会自己跑 Loop 的完整 Agent。

**边（Edge）**：节点之间怎么交接。不只是"先做 A 再做 B"，还能表达并行、条件、失败、重试和回退。

**共享状态（State）**：项目的公共工作台。需求、研究笔记、代码版本、测试结果、审查结论，都存在这儿，供后面的节点读。

**路由规则（Routing）**：决定下一步去哪。比如"测试通过就交付，测试失败就回实现节点，信息不足就回研究节点"。

用伪代码大概长这样：

```text
node 研究: 输出 research_notes -> state
node 实现: 读 research_notes, 输出 code -> state
node 测试: 读 code, 输出 test_result -> state
route: 测试通过 -> 交付 ; 测试失败 -> 实现 ; 资料不足 -> 研究
```

就这么点东西。你画地铁图、画流水线，画的就是 Graph。

## 演进：从 Prompt 到 Graph

这条演进路线，其实是 AI 一步步走向更复杂项目的路线。

**Prompt 阶段**。你说"生成一个网页"，它凭预训练记忆盲猜。像给实习生一句话命令，写出来的代码全凭运气。

**Context 阶段**。把技术栈、设计稿、API 文档都塞给它。有了项目上下文，写出来的代码不再"鸡同鸭讲"。

**Harness 阶段**。接上终端、沙箱、Git 和 MCP。AI 有了行动能力，从"写代码的文员"进化成能跑测试的 Coding Agent。

**Loop 阶段**。引入检查和控制逻辑。报错了不用人插手，它自己看日志、改代码、再跑测试，自我纠错。

**Graph 阶段**。面对大项目，拆成专业节点。研究节点负责调研写笔记，通过路由把状态传给实现节点去落地。

每一步，AI 都在处理更高复杂度的项目。Graph 不是空降的新概念，是前面所有阶段的自然延伸。

## 主流工具已经在用 Graph

你可能没意识到，手头的工具早就在跑 Graph 了。

**OpenAI Codex**：主 Agent 把探索、测试、日志分析这类独立工作委派给多个子 Agent，并行完成后返回摘要。官方也提醒：并行更适合读密集型任务，多个 Agent 同时改代码会增加冲突和协调成本。

**Claude Code**：Subagents 各自有独立上下文，负责代码审查、调试、资料分析。实验性的 AgentTeams 还加了团队负责人、共享任务列表和任务依赖：前置任务没完成，下游任务不能领。

**Cursor**：2.4 版本加了默认和自定义 Subagents；2.0 允许同一个 Prompt 最多启动 8 个 Agent，在独立 Git Worktree 或远程机器上试不同方案。

**Kimi Agent Swarm**：运行时动态成图，最多协调 300 个子 Agent，单个任务能完成 4,000 次以上工具调用。

**Coze Studio** 最诚实：把图直接摆在你面前，画布上连模型、插件、代码、子工作流节点，官方文档直接管它叫包含控制流和数据流的有向无环图（DAG）。

OpenAI 的 Alex Kotliarskyi 7 月 25 日给了个两步教程：先画一张 Graph（画纸上也行）；再把图交给 Codex，让它写代码、运行、实现这个工作流。"没有第三步。"

这套底层技术其实更早就有了。2024 年有 ChatDev 把软件开发组织成"软件公司"、MetaGPT 把标准作业流程写进多 Agent 框架、Anthropic 的《Building Effective Agents》总结提示链、路由、并行、编排者/工作者这些常见结构——画出来，就是不同形状的执行图。GPTSwarm 那篇论文标题干脆就叫《Language Agents as Optimizable Graphs》。

框架层更直接：LangGraph 把节点、边、共享状态、持久化、人工介入当核心能力；Google ADK 2.0 推出 Graph-first 引擎，节点和边由你定义，调度器管并发、状态持久化、暂停、恢复、重试和人工审批。

## 什么任务值得用 Graph

关键问题来了：是不是所有复杂任务都该上 Graph？

不是。"复杂"不只是步骤多。Nature Machine Intelligence 7 月 24 日那篇研究，覆盖 260 种配置、六类基准、五种架构、三家模型系列，结论一句话：不支持"Agent 越多越好"。

可拆分的金融任务，多 Agent 相对单 Agent 最高提升 80.8%；顺序依赖很强的 Plan Craft 规划任务，最高下降 70%；SWE-bench Verified 上，四类多 Agent 架构全都下降 1.3% 到 12.8%。

Anthropic 的案例也印证了边界：主 Agent 制订计划，子 Agent 并行搜索，最后交给引用检查 Agent 把关。适合广度搜索的任务，比单 Agent 高 90.2%。但代价是：普通 Agent 的 Token 消耗约是聊天模式的 4 倍，多 Agent 系统约 15 倍。

那什么任务适合 Graph？五条判断标准：

- **能拆分**：不同部分能交给不同节点独立完成，而不是所有步骤都依赖同一份完整上下文。
- **有分支或回退**：要根据测试、资料完整性或人工意见选不同路径。
- **中间状态值得保存**：需求、研究笔记、代码、测试结果要被后续节点复用。
- **结果能验收**：有测试、评分标准、规则检查或人工审批。
- **协作收益高于协调成本**：并行和专业分工的收益，能抵消上下文传递、结果合并、冲突处理的成本。

什么情况别用？改个按钮颜色、解释一段代码、生成一个简单页面，单 Agent 更快。每一步都严格依赖上一步、所有人都得共享完整上下文的任务，没必要为组队而组队。

还要算成本账：每加一个 Agent，就要准备上下文、调用模型、传递结果、汇总。职责不清会导致重复搜索、同时改同一个文件、一堆 Token 讨论彼此制造的问题。

黄仁勋在 Startup School 2026 说过：当底层实现越来越多被 Agent 自动化，人类的核心价值就从"亲手完成每个步骤"转向"设计系统、明确约束、组织信息流，并以细粒度方式控制 Agent"。

Graph Engineering，本质就是设计一个可观察、可路由、可约束、可局部修正的执行系统。

## 总结

回到开头那个问题：Loop 过时了吗？

没有。Loop 和 Graph 是互补，不是替代。Graph 的每个节点，都可能在自己的 Loop 里转。

新增的工程问题是：哪些 Loop 该存在、它们怎么交接、谁能改共享状态、失败后回到哪里、什么时候必须停下来。

工程师的注意力，正在从"怎样写一句更好的指令"，扩展到"怎样准备信息、提供工具、建立反馈，再把多个执行单元组织成一个可观察、可恢复、可控制成本的系统"。

Loop 让单个 Agent 跑得稳，Graph 让一群 Agent 走得远。
