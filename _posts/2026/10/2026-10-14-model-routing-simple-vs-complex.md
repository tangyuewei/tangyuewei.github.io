用 Opus 给变量改名，等了四秒，烧掉一笔钱；反过来用 Flash 去解分布式事务的死锁，它答非所问，你又回头重跑。模型选错档，三个代价是一起来的：慢、贵、还不准。

很多团队把"接一个最强模型"当成 Agent 的终点。其实那只是起点。同一个 Agent 一天里干的活，有的只是抽个字段，有的要动三个服务的架构。让它们全跑同一个最贵的模型，等于让总工程师去贴发票。

模型路由要回答就一件事：怎么让"该快快的活"跑 Flash，"该稳的活"跑 Max。

## 一、"一个模型打全场"为什么是错的

成本是按调用次数线性累积的。贵模型在非推理任务上并不会更准——抽一段 JSON 字段，任何档位都行，用 Max 只是更慢、更贵，准确率天花板由任务本身决定，不随档位上升。

延迟也会被放大。IDE 里的自动补全、实时的语法校验，这些场景等不起 Max 的那几秒。你把最慢的模型放在最快要求的地方，体验直接崩。

还有一类隐性浪费：贵模型的"思考预算"用在了不需要想的地方。一个布尔判定"这段是不是登录代码"，本可以一毫秒解决，却走了完整推理链，吞吐和账单一起涨。

## 二、三档分法：Flash / Medium / Max

分档只问一个问题：这个活，需不需要"想"？

**Flash（极速档）**——不需要思考链的活。分类、抽取、格式化、正则生成、简单翻译、布尔判定、摘要压缩。它们的共同特征是：输入输出模式固定、能用规则描述、错了能立刻被发现。这类活用最强模型是纯浪费。

**Medium（均衡档）**——大多数普通活。单文件 bug 修复、写样板代码和脚手架、总结一段文档、普通对话、改文案。需要一点推理，但范围可控、错了能重试，不必上最贵的档。

**Max（极致档）**——高难度活。跨文件的架构改动、难复现的并发和死锁 bug、安全敏感的分析、需要长链推理、或者一旦出错会引发昂贵返工的任务。这里省模型就是省错了地方。

档位不是模型品牌，是"能力水位"。Flash 对应 Haiku、Flash-lite 这一类；Medium 对应 Sonnet 这一类；Max 对应 Opus 这一类。厂商命名会变，分档逻辑不变。

## 三、怎么判断这个活是简单还是复杂

这是路由真正的难点。给一张判定清单，按从上到下的顺序走：

1. 能不能用正则、脚本、或确定性程序搞定？能——就别调模型，或只用 Flash 做一层壳。
2. 模式固定、结果可以立刻校验吗？可以——Flash。
3. 需要一点推理，但在单文件范围内、错了能重试吗？是——Medium。
4. 跨文件或跨系统、不可逆、高危、或需要长链推理吗？任一命中——Max。

![模型路由三档决策树](/imgs/202610/2026-10-14-model-routing-simple-vs-complex-infographic-1.jpg)

两个容易踩的反直觉信号：

- "看起来一句话"不等于简单。比如"帮我优化这个慢查询"，背后可能牵动全表结构和索引，该走 Max。
- "看起来复杂"不等于必须 Max。比如"把这段 Java 8 改成 Java 17"，大多是机械替换加少量适配，Medium 就够。

判断的本质，是看**失败成本**和**推理深度**，不是看描述长短。

## 四、编码里的活，归哪一档

把日常编码任务摊开，大部分其实落在 Flash 和 Medium，真正要 Max 的是少数。

| 活 | 档位 | 理由 |
| --- | --- | --- |
| 变量重命名、格式化、生成 getter/setter | Flash | 模式固定，IDE 即可，错立即见 |
| 写正则、小 SQL 查询、解析日志行 | Flash | 结果可立即验证 |
| 生成单元测试、补样板代码 | Medium | 需理解上下文，可重试 |
| 单文件 bug 修复 | Medium | 范围可控 |
| Code Review 初筛（找明显问题） | Flash / Medium | 模式化检查，低风险 |
| Code Review 终判、安全评审 | Max 或人 | 高危，需长链推理 |
| 重构核心模块 | Max | 跨文件，不可逆风险 |
| 修并发死锁、竞态 | Max | 难复现，返工贵 |
| 安全审计、注入研判 | Max | 高危，错一次代价大 |

一个常被忽略的点：Code Review 可以分两档。初筛用 Flash 先捞出空指针、未关闭资源这类模式化问题，终判和是否合入留给 Max 或人。这样既不漏明显的，也不让最贵的模型耗在啰嗦的格式化意见上。

## 五、工作里的活，归哪一档

路由不只用于写代码。凡是"模型替人干活"的地方，都能分档。

| 活 | 档位 | 理由 |
| --- | --- | --- |
| 邮件分类、打标签、提取要点 | Flash | 模式固定，错可立即发现 |
| 会议纪要整理、周报草稿 | Medium | 需归纳，但可复核 |
| 合同风险点初筛 | Medium | 初筛可跑，终判需人 |
| 战略分析、尽调研判 | Max | 高风险，推理深 |
| 客服标准问答 | Flash / Medium | 多数标准，少数升级 |
| 多文档对比归纳 | Medium | 跨文档，但容错尚可 |

规律是一样的：凡是"错了能马上看出来"的，尽量下沉到 Flash；凡是"错了要背责任或要返工"的，留在 Max 或交给人。

## 六、工程里怎么做路由

路由有两种落地方式，优先用简单的。

**静态路由**：按任务类型直接预设档。大部分场景这一层就够了，零额外延迟。比如"生成单元测试"永远走 Medium，"抽字段"永远走 Flash。

**动态路由**：让一个小模型先判断复杂度，再派发到对应档；或者同一模型用 think-token 开关——简单活直接关掉思考链。动态路由只在"静态分不清"的地方加，别为了省一点钱，加一层比任务还慢的路由。

顺手提一句成本侧的杠杆：系统提示和工具定义是每次调用都重发的静态前缀，把它们放在最前面并让缓存命中，能拿到不小的折扣。这点跟分档是互补的——分档管"用哪档"，缓存管"重复的部分少付"。

反模式要记牢：为省 0.01 美元加一层慢路由；路由判断本身漂移，把高危活误判成 Flash；还有"简单活不怕贵"——批量场景下，千万次 Flash 累积起来也是一笔钱，简单活也要算总量。

## 七、最小可行路由清单

别一上来就搭复杂系统，先照这六步走：

1. 盘一遍你的 Agent 实际在干哪几类活，按调用量排个序。
2. 把"模式固定、可立即校验"的活，全部降到 Flash。
3. 只把"跨系统、不可逆、高危、长链推理"留 Max。
4. 其余默认 Medium，不纠结。
5. 静态路由优先；动态路由只在确实分不清时加。
6. 埋个计数器：每档占比和单档成本，按月看趋势。

模型是资源，不是身份。选对档位，才是工程；一味上最贵的，只是花钱买心安。
